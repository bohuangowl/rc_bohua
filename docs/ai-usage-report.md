## 2. 我自主做出的关键决策

### 决策 1：投递语义选用 At-Least-Once
设计要求核心目标是"稳定可靠送达"，Exactly-Once 在外部 HTTP API 场景下不可实现，At-Most-Once 无法保证送达。At-Least-Once 是异步通知系统的主流方案，搭配下游幂等键去重即可有效降低重复影响。

### 决策 2：使用内存结构模拟任务队列，不引入 SQLite 或消息中间件
AI 最初设计的 README 中使用了 SQLite 作为队列存储。我判断 MVP 不需要持久化，改用线程安全的内存 dict。原因是：作业流量假设低（QPS < 10），内存队列足够承载；零外部依赖，降低部署和开发复杂度，符合 MVP 定位。

### 决策 3：指定模块结构
AI 最初提议用 queue.py / router.py / worker.py / models.py 的拆分方式。我调整为 config.py / task.py / deliver.py / server.py / main.py，将队列与模型合并到 task.py，路由与投递合并到 deliver.py，减少模块数量，代码结构更扁平直观。

### 决策 4：所有代码注释和配置值使用英文
AI 生成的代码包含中文注释和 docstring。我要求全部转为英文，避免编码问题导致潜在语法风险。文档文件（README、设计要求）保留中文。

### 决策 5：差异化重试策略
4xx 客户端错误（400/401/403/404/422）直接标记 FAILED，不重试；5xx 和网络超时走指数退避重试，最多 3 次后进入死信队列。4xx 代表配置或权限问题，重试无意义，只会浪费资源。

### 决策 6：测试文件合并
AI 将边缘用例测试放在独立的 `_edge.py` 文件中。我要求合并回主测试文件，减少文件数量，保持测试目录清晰。

## 3. AI 提出但未采纳的建议

### 建议 1：使用 SQLite 作为队列存储
AI 在首次 README 设计中使用了 SQLite 做队列持久化。我未采纳，改用内存队列。原因是 MVP 不需要持久化恢复能力，SQLite 增加文件 I/O 和部署步骤，与零外部依赖目标矛盾。持久化可放在 V2 引入 Postgres 时一并解决。

### 建议 2：引入 Flask / FastAPI 作为 HTTP 框架
AI 在依赖分析中将 Flask 和 FastAPI 列为备选方案，建议 V2 迁移。我认为 MVP 阶段 3 个 API 端点用 stdlib http.server 完全足够，引入 Web 框架增加外部依赖但收益微乎其微。V2 端点增多后可考虑迁移 FastAPI。

### 建议 3：实现多线程并发消费
AI 建议使用多线程 Worker 提升投递吞吐。我判断 MVP 流量场景下单线程轮询已经足够，多线程引入竞态条件和调试复杂度，与 MVP "优先保证功能正确"的目标冲突。

### 建议 4：增加结构化日志与文件持久化
AI 建议输出结构化 JSON 日志并写入文件。我认为 MVP 阶段控制台日志足够排查问题，日志落地是运维功能，放在 V3 可观测性阶段实现。

### 建议 5：增加熔断与限流组件
AI 在演进路线中将熔断和限流列为 V4 企业级能力。我确认此建议合理但不在 MVP 范围内，未采纳。
