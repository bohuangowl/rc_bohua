# APINotifyService — 内部统一 HTTPS 通知投递服务





## 项目简介 & 问题理解





### 业务背景





企业内部的多个业务系统（广告系统、CRM、库存系统等）在发生关键事件时，需要调用外部供应商提供的 HTTPS API 发送通知。常见场景包括：





- 用户通过第三方广告引流并注册成功 → 通知对应广告系统


- 用户订阅付款成功 → 通知 CRM 系统更新联系人状态


- 用户完成商品购买 → 通知库存系统变更库存





### 核心问题





1. **外部 API 异构** — 不同供应商的请求地址、Header 格式、Body 结构各不相同，上游业务系统如果直接对接，每接入一个供应商就要改一次上游代码。


2. **外部系统不可靠** — 供应商 API 可能超时、限流、返回 5xx，上游业务系统并不关心返回值，但业务要求通知"稳定可靠送达"。


3. **耦合** — 上游业务逻辑与通知投递的成败耦合在一起，降低了核心链路的稳定性。





### 设计思路





在内部业务系统和外部供应商 API 之间插入一个**异步投递服务**。上游只负责"把通知丢进来"，本服务负责"保证通知最终送达"。格式转换、路由、重试、失败处理全部由本服务接管。

### 核心流程





1. **接收** — 上游系统通过 HTTP POST 将通知请求发送到本服务，请求中包含目标供应商标识、业务负载、幂等键。


2. **持久化** — 服务将通知存入本地队列（MVP 阶段使用 SQLite），返回 202 Accepted，上游即可继续做自己的事。


3. **投递** — 后台 Worker 从队列中取出待投递的通知，根据供应商配置构造对应的 HTTP 请求并发送。


4. **重试** — 投递失败（超时、网络错误、5xx）时，Worker 按指数退避策略重新投递。


5. **终态** — 投递成功标记为 delivered；超过最大重试次数进入死信队列（dead letter queue）标记为 dead_lettered。





### 技术栈





| 组件 | MVP 选择 | 理由 |


|------|----------|------|


| 语言 | Python 3.10+ | 限制要求 |


| HTTP 框架 | 标准库 http.server | 零外部依赖，MVP 够用 |


| 存储 | SQLite | 零运维，文件即数据库；队列也复用同一存储（见依赖分析） |


| 队列调度 | SQLite + 轮询 Worker | 零外部依赖，实现简单；见下方"关键依赖与替代方案"分析 |


| 配置 | JSON / YAML 文件 | 简单易改 |

## 系统边界定义





### 本系统解决的问题





| 问题 | 方案 |


|------|------|


| 上游系统与外部 API 格式不匹配 | 通过供应商模板配置，由本服务统一做格式转换和路由 |


| 外部 API 不稳定导致的投递失败 | 队列持久化 + 自动重试 + 指数退避 |


| 上游系统无需关心投递结果 | 异步投递，上游收到 202 即返回 |


| 重复通知 | 支持幂等键去重（基于 idempotency_key） |


| 投递失败后的人工介入 | 死信队列记录，后续可导出或重投 |





### 本系统不解决的问题（及原因）





| 不解决的问题 | 原因（MVP 视角） |


|-------------|------------------|


| 供应商 API 认证/鉴权 | 该层属于外部系统安全范畴，MVP 假设供应商配置已预先配好认证凭证；后续可在 HTTP Client 层统一接入 Token 刷新 |


| 上游认证与鉴权 | MVP 假设部署在内网或受信任网络环境；生产环境应前置 API Gateway / JWT 校验 |


| 实时投递状态回调 | 上游不关心返回值是硬性约束，通知终态可通过查询 API 主动获取 |


| 可视化 Dashboard | MVP 不引入前端，靠日志 + 数据库查询即可排查问题 |


| 多副本/高可用部署 | SQLite 不支持并发写入，MVP 只需要单进程可用；后续可替换为 Postgres + 无状态多 Worker |


| 供应商限流适配 | MVP 假设外部 API 有足够的容量；后续可通过令牌桶做限流保护 |


| 消息队列中间件（RabbitMQ/Kafka） | SQLite 作为队列对 MVP 级别流量足够，零运维成本 |

## 可靠性方案、失败处理策略、投递语义





### 投递语义：至少一次（At-Least-Once）





**选择理由：**





- "至少一次" 是最符合业务约束的选择。上游不关心返回值，但业务要求"稳定可靠送达"。


- **恰好一次（Exactly-Once）** 在涉及外部 HTTP API 的分布式场景下几乎不可能实现——外部系统的响应可能丢失、请求可能超时但实际已处理、外部系统不支持幂等消费，这都需要外部系统的配合。


- **至多一次（At-Most-Once）** 投递一次失败即丢弃，无法满足"可靠送达"的要求。


- **本服务的折中**：通过幂等键（idempotency_key）尽量降低"至少一次"带来的重复投递概率，同一 Key 的重复请求会被去重，但无法约束外部系统的去重行为。MVP 阶段充分理解这一局限。





### 失败处理策略





#### 投递重试机制





| 失败类型 | 处理方式 |


|----------|----------|


| 网络超时 / 连接失败 | 直接重试，计入重试次数 |


| 5xx 服务端错误 | 直接重试，计入重试次数 |


| 4xx 客户端错误（400/401/403） | 不重试，直接标记为 failed（供应商端配置问题，重试无意义） |





#### 重试策略





- 最大重试次数：**3 次**（MVP 阶段硬编码）


- 退避策略：**指数退避** — 第 n 次重试在 2^n × 10 秒后执行（即 10s → 20s → 40s）


- Worker 定期轮询数据库，取出 status = 'pending' 且 next_retry_at <= now() 的通知进行投递





#### 终态处理





- delivered — 投递成功，不再处理


- failed — 收到 4xx 错误，立即终态，不重试（配置问题，人工介入）


- dead_lettered — 超过最大重试次数仍未成功，进入死信队列





#### 死信队列





- 死信通知不丢弃，保留在数据库中标记 dead_lettered


- 提供查询接口 (GET) 和手动重投接口 (POST) 供人工介入

## 工程决策与设计取舍





### 必要设计 vs 过度设计





| 设计 | 决策 | 理由 |


|------|------|------|


| 消息持久化 | ✅ 必要 | 进程崩溃不丢消息是可靠性的底线 |


| 指数退避重试 | ✅ 必要 | 防止对故障外部系统造成"重试风暴" |


| 供应商配置分离 | ✅ 必要 | 添加新供应商不应改代码 |


| 幂等去重 | ✅ 必要 | 防止网络重试导致上游重复请求引发重复投递 |


| 死信队列 | ✅ 必要 | 失败数据要有明确出口，不能石沉大海 |


| 监控告警 | ❌ 过度（MVP 砍掉） | 生产级必需，但 MVP 用日志 + 数据库查询替代 |


| 多供应商并发限流 | ❌ 过度（MVP 砍掉） | 假设外部 API 容量足够，后续通过令牌桶补上 |


| 消息队列中间件（RabbitMQ/Redis Streams） | ❌ 过度（MVP 砍掉） | 见下方"关键依赖与替代方案"的完整分析 |


| 任务调度框架（APScheduler 等） | ❌ 过度（MVP 砍掉） | 见下方"关键依赖与替代方案"的完整分析 |


| Web Dashboard | ❌ 过度（MVP 砍掉） | 管理后台对 MVP 无必要，CLI + SQL 够用 |


| 配置热加载 | ❌ 过度（MVP 砍掉） | 重启服务加载配置在 MVP 阶段是可接受的 |


| 分布式一致性 | ❌ 过度（MVP 砍掉） | 单进程 + SQLite，根本不需要 |





## 关键依赖与替代方案分析





> 以下分析覆盖 MVP 阶段的核心依赖选择，每个选项说明：为何选它、不选它的替代方案是什么、什么条件下应该换。





### 1. 队列存储：SQLite — 为什么不用 RabbitMQ / Redis Streams？





**MVP 选择：SQLite**





选 SQLite 的核心逻辑：





1. **MVP 流量假设** — 内部业务系统的大事件通知频率通常不高（QPS < 10）, SQLite 作为队列可以轻松应对。瓶颈在外部 API 响应时间, 而不是队列吞吐。


2. **零运维** — SQLite 不需要额外进程、不需要集群、不需要运维手册。app.db 一个文件就是全部。


3. **事务语义** — 入队 + 去重 + 状态更新可以在一个事务中完成, 不需要分布式协调。


4. **可排查** — 通知状态直接在数据库里, SELECT 查询即可拿到全部信息。





**替代方案及其代价：**





| 方案 | 优势 | MVP 阶段的代价 |


|------|------|---------------|


| RabbitMQ | 原生 AMQP、内置死信队列、Consumer 分组 | 需要部署 Erlang VM + RabbitMQ 服务, 运维负担高。消息路由、交换机、绑定等概念对 MVP 场景过度 |


| Redis Streams | 轻量、高性能、Consumer Groups | 内存占用与持久化折中。需要单独部署 Redis。MVP 阶段引入 Redis 只为了当队列用, 性价比低 |


| 文件系统队列 | 最简单 | 没有事务保证, 断电/崩溃场景容易丢消息。排查困难 |





**什么条件下应该换？**





- QPS > 1000: SQLite 写锁成为瓶颈


- 需要多个消费者并行消费: SQLite 不支持并发写


- 需要消息路由 / pub/sub 模式: SQLite 没有原生支持





届时优先推荐 **Redis Streams** (如果组织已有 Redis 则零额外运维成本), 次选 **RabbitMQ**.





### 2. 调度机制：轮询 Worker — 为什么不用 APScheduler / Celery Beat？





**MVP 选择：轮询 Worker**





Worker 每隔 N 秒查询一次数据库, 取出 next_retry_at 已到期的通知进行投递。





选轮询的理由：





1. **重试调度的本质是时间条件查询** — next_retry_at <= now() 是一个简单的 WHERE 条件, 不需要调度框架来管理。


2. **指数退避可计算** — 第 n 次重试在 2^n x base_interval 秒后执行, 这个值在每次重试时计算并写入 next_retry_at 即可。不需要 cron 表达式。


3. **零依赖** — 轮询只需要一个 time.sleep() + threading.Thread, 不需要引入任何第三方库。





**替代方案：**





| 方案 | 优势 | MVP 阶段的代价 |


|------|------|---------------|


| APScheduler | 支持 cron / interval / date 触发器, SQLite 作业存储 | 增加一个外部依赖。对 MVP 场景来说, 轮询的 5 行代码和 APScheduler 的 20 行配置 + 文档阅读成本相比, 轮询更简洁 |


| Celery Beat | 支持持久化调度、分布式 Worker | 需要 Redis/RabbitMQ 作为 Broker, 对 MVP 过度设计 |





**什么条件下应该换？**





- 需要**每个供应商独立的重试窗口** (比如供应商 A 在 9-18 点才允许重试)


- 需要**固定窗口限流**与调度联动 (比如每分钟最多重试 10 次)


- 需要**分布式 Worker** 协调调度防止重复执行





届时推荐 **APScheduler**, 因为它在单进程内就可以运行, 不需要额外的 Broker.





### 3. HTTP 框架：标准库 http.server — 为什么不用 Flask / FastAPI？





**MVP 选择：http.server (标准库)**





理由很简单：MVP 只有 3 个 API 端点 (POST 接收通知、GET 查询、POST 重投), 路由逻辑不超过 50 行。标准库完全可以胜任。





**替代方案：**





| 方案 | MVP 阶段代价 |


|------|-------------|


| Flask | 引入一个 Web 框架依赖, 对 3 个端点来说太重 |


| FastAPI | 依赖 Pydantic + Uvicorn, 好处是自动文档和请求校验。如果团队习惯 FastAPI, V2 值得迁移 |





**什么条件下应该换？**





- 端点数量 > 10, 路由管理变得混乱


- 需要请求体校验、OpenAPI 文档、异步处理


- 需要 Middleware (认证、限流、日志)





届时优先推荐 **FastAPI**, 因为它的请求校验和自动文档在中大型 API 项目中可以显著减少样板代码。





### 4. 存储引擎：SQLite — 为什么不用 Postgres？





**MVP 选择：SQLite**





SQLite 的零运维在 MVP 阶段是压倒性优势。不需要安装数据库服务器、不需要配置连接池、不需要备份策略。app.db 文件备份就是数据库备份。





**什么条件下应该换？**





- 需要多进程 / 多机器并发写入 -> 切换到 **Postgres**


- 需要更复杂的查询和分析 (GROUP BY 多表 JOIN 等) - SQLite 也能做, 但 Postgres 更强


- 需要对队列做行级锁 (SKIP LOCKED) - SQLite 不支持 SKIP LOCKED, 高并发队列消费会冲突





届时推荐 **Postgres**, 搭配 SKIP LOCKED 实现 Worker 竞争消费。

### 开发者体验决策





- **零外部依赖** — MVP 使用 Python 标准库（http.server, sqlite3, urllib.request），pip install 都不需要，降低上手成本
